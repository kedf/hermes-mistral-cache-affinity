# hermes-mistral-cache-affinity

French version: [README.fr.md](README.fr.md)

A Hermes plugin (`llm_request` middleware) that adds the `x-affinity` header
with the `prompt_cache_key` already generated by Hermes, only for HTTPS Chat
Completions requests to `api.mistral.ai` and `api.eu.mistral.ai`.

The goal is to stabilize Mistral-side cache routing to improve prompt cache
hits. Before this plugin, Mistral sessions plateaued around 25% cache hit;
with the plugin, observed sessions reach 93–95% (see
`verification/live-report.json` and the `agent.log` `cache=` lines).

## What the plugin does

- If the request is `chat_completions` mode, over HTTPS, to an allowed
  Mistral host, and carries a non-empty `prompt_cache_key`: it adds
  `x-affinity: <prompt_cache_key>` to `extra_headers`.
- It changes **neither** the messages, **nor** the tools, **nor** the system
  prompt, **nor** the cache key. The original request is not mutated (the
  middleware returns a copy).
- An explicit `x-affinity` header (any case) is preserved: the plugin does
  nothing.
- Without a cache key, on another provider, another host, a non-HTTPS scheme
  or another API mode: the plugin does nothing.
- No network access, secret, history or logging is performed by the plugin;
  the network call remains the Hermes client's own.

## Install

Copy (or symlink) this directory into the `plugins/` directory of the
Hermes profile concerned:

```bash
cp -r hermes-mistral-cache-affinity ~/.hermes/profiles/<profile>/plugins/
```

Then enable the plugin in the profile's `config.yaml`:

```yaml
plugins:
  enabled:
    - mistral-cache-affinity
```

Disable: `hermes plugins disable mistral-cache-affinity` in the profile
concerned.

> This plugin does not choose the endpoint: it applies to both
> `api.mistral.ai` and `api.eu.mistral.ai`. Set the Mistral provider's
> `base_url` (e.g. `https://api.eu.mistral.ai/v1`) in your Hermes config to
> pick a region.

## Limitations

- This is a cache **routing** improvement, not a cache-hit guarantee. A
  prefix change, an expiry or provider behavior can still cause a cache miss.
- Scope is the Hermes `llm_request` middleware; do not assume every
  auxiliary call goes through this middleware.

## Tests

```bash
# Unit tests (synthetic, no network)
python -m unittest discover -s tests -p 'test_affinity.py' -v

# Integration tests (require a hermes-agent checkout on sys.path)
python -m unittest discover -s tests -p 'test_integration.py' -v

# Live test against the Mistral API (opt-in, synthetic prompts only)
LIVE_MISTRAL_CACHE_TEST=1 \
LIVE_REPORT_PATH=verification/live-report.json \
MISTRAL_API_KEY=... \
python -m unittest discover -s tests -p 'test_live.py' -v
```

Live tests are opt-in, with bounded output and no automatic retries. Reports
keep only counters, latencies and SHA-256 fingerprints — never API keys or
conversations.

## Related work

- [fengrunda/hermes-deepseek-cache](https://github.com/fengrunda/hermes-deepseek-cache) —
  same problem class (cache hit plateauing ~25%) on DeepSeek, solved by
  "wire shaping" (stripping `reasoning_content` from non-tool-call turns).
  Complementary approach: here the request body is never modified, only the
  `x-affinity` header is added.
- The `x-affinity` mechanism is a cross-harness standard: OpenClaw, Pi, Zed
  and others send `x-affinity: <sessionId>` to Mistral for KV-cache reuse.
  Hermes already generates a `prompt_cache_key` (`supports_prompt_cache_key=True`)
  but never sent it as a header; this plugin closes that gap.

## Upstream context

This plugin addresses a known, documented problem in
`NousResearch/hermes-agent`: prompt cache invalidation between turns
(unstable prefix, timestamps, tool ordering, provider drift). See in
particular:

- #27339 — KV cache invalidation from "dynamic tool shuffling"
- #18547 — unstable system prompt prefix (timestamps, memory counters)
- #128817 — follow-up turns re-prefill (tool schemas change between turns)
- #133575 — cache "stuck" at a fixed floor on a plugin provider
- #79602 — let a ProviderProfile declare its prompt-cache policy
